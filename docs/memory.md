# 内存曲线：共享合成器与共享 /usr（2026-11-16 至 17，已测）

问题：N 个 agent 同时运行时，总内存怎么增长？Heddle 设计里的两种共享各省多少：

- 多个 agent 共用一个合成器（对照：每个 agent 一个独立合成器）。[隔离与共享](isolation.md) 估计这部分只省几十 MiB（未测）。
- 所有 agent 共用只读 `/usr`，文件页只存一份（对照：每个 agent 一份 `/usr` 拷贝，近似每个 agent 一个独立镜像）。

这是 README 计划第 4 步的第一组数据，也是 [门槛实验](gate.md) 把重心转到内存之后的第一步。

## 设置

- 环境：与门槛实验相同（OrbStack 开发容器，Debian trixie，arm64，12 GiB 内存，wlroots 0.18，pixman，1920x1080，root 运行）。全程没有用到交换区（SwapPss 为 0）。
- 应用：Chromium（本地表单页，`--no-sandbox`）、GNOME Text Editor、LibreOffice Writer。每个 agent 一个应用实例，全部经 `heddle-run` 启动在各自的 bubblewrap 里（独立 HOME、/tmp、D-Bus 会话，默认断网），出帧策略 `observe`。
- 配置：
  - `shared`：一个 Heddle 进程服务全部 agent，所有沙盒绑定宿主 `/usr`。
  - `per-comp`：每个 agent 一个 Heddle 进程，仍共用 `/usr`。
  - `per-usr`：一个 Heddle 进程，每个沙盒绑定自己的一份 `/usr` 拷贝（`cp -a`，在 overlay 上是不同的 inode，因此页缓存不共享）。合成器本身仍用宿主 `/usr`。
- 流程：每个 N ∈ {1, 2, 4, 8} 依次启动 N 个应用（间隔 1 s），等全部出窗口，再等 15 s；每个 agent 敲两行字并截图；再等 10 s 后采样。每组只跑 1 次。
- 指标：合成器与各沙盒内全部进程（bwrap、dbus-run-session、dbus-daemon、AT-SPI、应用）的 PSS 之和。PSS 把共享页按映射它的进程数分摊，所以总和就是这些进程实际占用的常驻内存，并按匿名页、文件页、共享内存（主要是 wl_shm 窗口缓冲）拆分。不含内核内存（页表、slab、套接字缓冲）和未映射的页缓存。
- 复现：`docker run --rm --privileged -v "$PWD":/src -w /src heddle-apps bench/memcurve.sh "1 2 4 8" 1`。`per-usr` 需要 N 份 `/usr` 拷贝，每份约 2 GiB 磁盘。

所有 36 组都出了窗口、截图判为稳定。

## 解读

- **共享 `/usr` 是主要的节省。** 共享时文件页几乎不随 N 增长（Chromium 236 → 248 MiB），不共享时线性增长（每个 agent 约 105–236 MiB）。N=8 时总内存少 35–48%：Chromium 少 1.6 GiB，Text Editor 少 0.7 GiB，Writer 少 0.9 GiB。每多一个 agent 的成本从 260–429 MiB 降到 156–196 MiB。
- **共享合成器在内存上没有可测的收益。** `per-comp` 反而比 `shared` 小 0–9 MiB，在单次运行的噪声之内。原因是 N 个 Heddle 进程的代码和库本身就通过页缓存共享，每个进程自己的匿名内存只有约 2 MiB；而按 agent 计的大头（窗口缓冲、输出缓冲）不论合成器是否共享都一样多。[隔离与共享](isolation.md) 估计的"几十 MiB"偏高，实测接近零。注意这里的 `per-comp` 仍共用 `/usr`；如果每个合成器来自不同的镜像，每个还要多几 MiB 文件页。
- **剩下的边际成本几乎全是匿名页。** 共享 `/usr` 后，每个 agent 的边际成本里约 75–85% 是应用自己的匿名内存（堆、JS 引擎、渲染缓存），其余主要是 1080p 窗口缓冲（每块约 8 MiB，应用和合成器各持有几块，合计每个 agent 24–43 MiB）。
- **重复的文件页是"可回收"的。** 三种配置下 `MemAvailable` 的下降几乎相同（Chromium N=8 都约 1.8 GiB），因为内核把干净的文件页算作可回收。也就是说，不共享 `/usr` 时多出的 0.7–1.6 GiB 在内存紧张时可以被换出，代价是缺页时从磁盘重新读入。硬性的上限由匿名页和共享内存决定，这部分三种配置一样。共享 `/usr` 的实际收益要在内存压力下测，见下面"内存压力下"一节。

## 结论（暂定）

- 保留共享只读 `/usr`：它在常驻内存上省 35–48%，并在内存紧张时避免重复的代码页互相挤出。
- 共享合成器不再以内存为理由。它和"每 agent 一个合成器"在内存上打平，是否共享应按其他因素决定：共享合成器是所有 agent 的可信计算基，崩溃会影响全部 agent（README"已知风险"）；每 agent 一个合成器隔离更好，但多出 N 个进程和控制端点。就这组数据，每 agent 一个合成器是可行的默认值。
- 下一个内存杠杆是匿名页，按 [隔离与共享](isolation.md#内存共享) 的候选：先用 KSM 统计 N 个同类实例匿名页中内容相同的比例；其次是窗口缓冲（降低分辨率，或在停帧期间释放输出缓冲）。

## 内存压力下：缺页与步耗时（2026-11-17，已测）

上面说重复的文件页"可回收"，这一节量化回收的代价：给定同样的内存上限，共享与不共享 `/usr` 各要付出多少缺页和读盘，步耗时变多少。

### 设置

- 把合成器和 8 个 agent 的沙盒放进一个 cgroup v2，`memory.max` 设为上限，`memory.swap.max` 设为 0。这样匿名页和共享内存不能回收，只有文件页能被换出；匿名页放不下就会 OOM。
- 每次运行前 `sync` 并清空页缓存，让所有文件页都由这个 cgroup 首次读入、计入它的用量。否则之前读入的页记在别的 cgroup 上，会绕开上限。
- 配置只比 `shared` 与 `per-usr`。上限按不限时的用量选：Chromium 共享时稳定在 1.86 GiB、不共享 4.0 GiB，匿名页加共享内存约 1.59 GiB；Writer 分别是 1.52 GiB、2.5 GiB、1.34 GiB。
- 流程：启动 8 个应用，全部出窗口后等 10 s；然后 5 轮，每轮依次对每个 agent 敲一行字、回车、截图，轮间等 3 s。统计这一阶段（约 33 s，40 步）cgroup 的主缺页、被回收后重新读入的文件页（`workingset_refault_file`）、磁盘读入量，以及每步耗时（敲字加截图的总时间）。每组 1 次。
- 复现：`docker run --rm --privileged -v "$PWD":/src -v heddle-usr:/var/tmp/heddle-usr -w /src heddle-apps bench/pressure.sh chromium "0 3000 2500 2200 2000 1800"`。

### 结果

所有组合都是 8/8 出窗口，没有 OOM，没有截图超时，结束时应用全部存活。

### 解读

- **不共享 `/usr` 时，一碰到上限就开始反复读盘。** 上限低于它的用量后，同样约 33 s 的 40 步里，Chromium 读盘从 137 MiB 涨到 3–56 GiB，最紧的一档到 732 GiB（约 18 GiB/s）；Writer 涨到 0.4–30 GiB。主缺页比共享时多两到三个数量级。原因是 8 份代码页互相挤出：一个 agent 读进来的页把另一个 agent 的同一段代码换出去。
- **共享 `/usr` 在同样的上限下几乎不受影响。** 上限只要不低于它自己的用量（Chromium 1.86 GiB、Writer 1.52 GiB），主缺页和读盘就和不限时一样。Chromium 压到 1800 MiB（已低于用量）时才开始读盘，也只有 315 MiB，是不共享时的 1/2000。
- **在这台机器上，步耗时几乎没变。** 不共享时 p50 最多慢 4–6%，只有 Chromium 最紧的一档慢了约 50%（389 → 593 ms，最大 1065 ms）。但这是因为这里的"磁盘"极快：容器的虚拟盘由 macOS 宿主的内存缓存支撑，能读到 18 GiB/s。同样的读盘量放到真实磁盘上会直接变成延迟：按 NVMe 约 3 GiB/s 算，Chromium 在 2000 MiB 一档的 56 GiB 要读约 19 s，超过这一阶段时长的一半；按云盘约 0.2–0.5 GiB/s 算，从 2500 MiB 一档起就读不过来。所以步耗时的数字是下限，读盘量才是可移植的结论。
- **没有 OOM。** 所有上限都高于匿名页加共享内存的硬下限，所以两种配置都能跑，区别只在读盘。再往下压，两种配置会在同一个点 OOM。

### 小结

共享 `/usr` 的价值在内存压力下才显现：同样 8 个 Chromium，共享时 2 GiB 就能安静地跑；不共享时要 4 GiB 才不读盘，压到 2 GiB 会在 33 s 里读 56 GiB。也就是说，在同样的内存和可接受的读盘量下，共享 `/usr` 能多放约一倍的 agent。这个结论对 Writer 同样成立，只是量级小一些。

不能据此下定论的地方：

- 每组只跑 1 次，应用基本空闲（打开一个页面或空文档、敲两行字）。真实任务中打开大文档、加载网页、运行扩展后匿名页会大得多，共享 `/usr` 的相对比例会下降。
- 没有测 VS Code。Chromium 只是近似，Electron 应用另带 Node 进程和扩展宿主。
- 内存压力实验的步耗时受宿主内存支撑的虚拟盘影响，偏乐观；需要在真实磁盘上复测延迟。没有记录压力下的 CPU 开销（回收和读盘本身要花 CPU）。
- 不限内存时，不共享配置在稳定阶段也有少量重读（Chromium 137 MiB），可能来自虚拟机整体的页缓存回收，没有查清。
- PSS 不含内核内存。N 个沙盒各有自己的 dbus-daemon 和 AT-SPI 进程，合计每个 agent 约 1–2 MiB，已计入总数。

## 一个 agent 的完整记账（2026-11-19，已测）

前面的 PSS 和匿名页统计只覆盖进程映射的内存。这一节把一个 agent 的沙盒状态算全（`bench/census.py`）：每个 agent 和合成器各放进一个 cgroup，读 `memory.stat`；内核部分另行估计；再统计各 agent 私有文件的磁盘占用和页缓存、沙盒内 tmpfs，以及内核对象的数量。每个应用 4 个 agent，表中是每个 agent 的平均值。

OrbStack 内核以 `cgroup.memory=nokmem,nosocket` 启动，内核内存和套接字缓冲不按 cgroup 记账。所以页表、内核栈、slab 用系统 `/proc/meminfo` 在启动前后的差值除以 N 估计（含合成器的份额），页表另用逐进程的 `VmPTE` 对照，两者一致。套接字缓冲没有测。

| 每个 agent（MiB） | Text Editor | Writer | Chromium |
|---|---|---|---|
| 匿名页 | 121 | 140 | 156 |
| 共享内存（窗口缓冲、memfd、共享内存段） | 15.8 | 8.5 | 28.7 |
| 合成器分摊（其中输出缓冲） | 20.6（15.9） | 20.3（15.9） | 18.9（15.9） |
| 页表 | 1.6 | 1.5 | 6.9 |
| 内核栈 | 0.7 | 0.4 | 2.1 |
| slab | 0.1 | 0.3 | 1.4 |
| **合计（不含共享文件页）** | **约 160** | **约 171** | **约 214** |
| 私有文件：磁盘 / 页缓存 | 1.8 / 1.0 | 0.3 / 0.3 | 2.2 / 0.8 |
| 沙盒内 tmpfs（`/dev/shm`、`/run`） | 0 | 0 | 0 |
| 进程 / 线程 | 8 / 43 | 9 / 24 | 16 / 131 |
| 文件描述符 / 套接字 / memfd | 92 / 21 / 2 | 110 / 24 / 1 | 426 / 83 / 31 |
| 挂载点（沙盒内） | 29 | 29 | 29 |

计入各 agent cgroup 的页缓存还有 9–64 MiB，但它们主要是这个 agent 首次读入的共享 `/usr` 文件页（谁先读就记在谁名下），不是它私有的，没有算进合计。

### 解读

- **匿名页之外的部分合计每个 agent 约 30–60 MiB。** 最大的是窗口相关的缓冲：应用侧的窗口缓冲 9–29 MiB，加上合成器侧每个 agent 两块 1080p 输出缓冲约 16 MiB。按观测出帧时，这些缓冲在停帧期间都可以释放或压缩，是另一个和 agent 节奏相关的杠杆。
- **内核状态很小，但 Chromium 的页表不可忽略。** Text Editor 和 Writer 的页表、内核栈、slab 合计约 2–3 MiB；Chromium 约 10 MiB，其中页表 6.9 MiB，来自 16 个进程和 V8、PartitionAlloc 的大块地址预留。
- **合计和内存曲线的边际成本对得上。** 这里的合计（160–214 MiB）与 [上面](#结果) 测的"每多一个 agent"（156–196 MiB）一致，多出来的主要是这里算进了合成器分摊和内核部分。
- **磁盘上的私有状态现在几乎为零。** 刚启动的 profile 只有 0.3–2.2 MiB，沙盒的 tmpfs 也是空的。真实任务里浏览器缓存、下载、打开的文档会让这部分增长，它影响的主要是磁盘和页缓存，以及快照和迁移的大小。

### 和虚拟机对比

[设计依据](design.md#对-agent-无用的桌面机制分析未验证) 中 OSWorld 虚拟机约 3.5 GiB：约 1.7 GiB 客户机页缓存、约 0.8 GiB 桌面外壳和显示（RSS）、约 420 MiB 对 agent 无用的服务（RSS）、0.5–0.8 GiB 碰过但已空闲的页、每台一份客户机内核，任务应用本身 279 MiB（RSS）。Heddle 下一个 agent 合计约 160–214 MiB，大约是它的 1/15–1/20。这个倍数主要来自共享内核和页缓存、去掉为人设计的桌面，而不是 Heddle 自己的机制。两边环境不同（x86 完整 GNOME 加 OSWorld 任务，对比 arm64 容器里基本空闲的应用），虚拟机一侧只有一次按 RSS 的快照，严格对比需要在同一台 x86 主机上用同一个任务分别测。
