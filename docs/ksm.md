# 匿名内存：重复、压缩与构成（2026-11-17 至 19，已测）

问题：[内存曲线](memory.md) 显示共享 `/usr` 之后，每个 agent 的边际成本里 75–85% 是应用自己的匿名内存。N 个 agent 跑的是同一个应用，这些匿名页里有多少内容相同、能按页合并（KSM 的做法）？重复主要出在同一 agent 内部，还是跨 agent？

## 方法

OrbStack 的内核没有编进 KSM，而且 KSM 是全局设置，开了会影响整个虚拟机。所以不开 KSM，直接读页内容统计 KSM 最多能合并多少（`bench/ksmscan.py`）：

1. 启动合成器和 8 个 agent（每个一个应用，经 `heddle-run`），放进一个 cgroup；全部出窗口后等 15 s，每个 agent 敲一行字并截图。
2. 冻结 cgroup，对每个进程用 `PAGEMAP_SCAN` 找出常驻匿名页（不含文件页、shmem、内核零页），用 `/proc/PID/pagemap` 的物理页号去掉已经写时复制共享的页，从 `/proc/PID/mem` 读内容做哈希。
3. 解冻，每个 agent 再做一步动作，20 s 后再扫一次。两次之间内容不变的页算"稳定"：KSM 只合并两轮扫描之间没变的页，所以稳定页上的重复才是实际能省的。
4. 分三类统计可省的页：全零页；非零页里只在同一 agent 内部（多个进程之间或同一进程内）重复的；必须跨 agent 合并才能省的。
5. 每个应用跑两次：默认（开地址随机化）和用 `setarch -R` 关闭地址随机化。地址随机化让每个进程的指针不同，含指针的页就不可能跨进程相同；关掉它是"从同一模板克隆出 N 个实例"的粗略近似。

环境同前（arm64 容器，pixman，1080p，`observe` 策略）。每组 1 次，扫描 8 个 agent 只要 1–2 s。

## 结果

8 个 agent，第二次扫描（MiB）：

| 应用 | 地址随机化 | 匿名页总量 | 全零页 | 非零，agent 内部 | 非零，跨 agent | 合计可省 | 只算稳定页 |
|---|---|---|---|---|---|---|---|
| Text Editor | 开 | 987 | 205 | 83 | 14 | 303（31%） | 301 |
| Text Editor | 关 | 991 | 207 | 83 | 90 | 380（38%） | 378 |
| Writer | 开 | 1143 | 7 | 128 | 123 | 258（23%） | 225 |
| Writer | 关 | 1143 | 7 | 129 | 275 | 410（36%） | 377 |
| Chromium | 开 | 1216 | 110 | 76 | 63 | 249（20%） | 238 |
| Chromium | 关 | 1218 | 110 | 411 | 177 | 697（57%） | 686 |

可省的页按内存区类型分（地址随机化开 → 关）：

- Text Editor：主要在 `[heap]`（185 → 188）和匿名映射（114 → 120）；关掉随机化后多出 72 MiB 库的私有页（`file-private`）。
- Writer：`[heap]` 142 → 217，匿名映射 115 → 126，库的私有页 1 → 67。
- Chromium：匿名映射 227 → 240；库的私有页 3 → 439。

## 解读

- **默认配置下，按页合并能省 20–31%，但其中大部分不需要跨 agent。** Text Editor 的可省部分有三分之二是全零页（205 MiB，占匿名页的 21%）。跨 agent 的非零重复只有 14–123 MiB，平均每个 agent 2–15 MiB。也就是说，对冷启动的独立实例，KSM 的收益主要来自零页和进程内部的重复，"N 个同构 agent"这一点几乎没被利用上。
- **地址随机化是跨 agent 共享的主要障碍。** 关掉它后，跨 agent 的非零重复翻 2–6 倍（Text Editor 14 → 90，Writer 123 → 275，Chromium 63 → 177 MiB），合计可省升到 36–57%。
- **Chromium 最大的一块是重定位后的库页。** 关掉随机化后，库的私有页（`file-private`）可省 439 MiB，每个 agent 约 55 MiB。这是 Chromium 主程序加载后做重定位写入的只读数据段（RELRO）：每个进程的加载地址不同，重定位结果就不同，只能各存一份；地址相同则逐字节相同。一个 agent 内的浏览器、GPU、工具进程各自加载一次，所以这部分在 agent 内部也会重复。Android 上的 Chrome 专门在进程间共享 RELRO 来省这块内存。
- **这些重复大多是稳定的。** 只算两次扫描之间没变的页，可省量只少 1–13%（Writer 下降最多），所以 KSM 实际能拿到其中大部分。
- **全零页是最便宜的一块。** Text Editor 21%、Chromium 9% 的匿名页全是零（Writer 几乎没有），不需要 KSM，用内核的零页去重或压缩就能回收。

## 结论（暂定）

- 对独立冷启动的 agent，按页去重能省 20–30%，主要靠零页和进程内重复，"同构"带来的额外收益很小。
- 要真正利用 N 个实例相同这一点，需要让它们的内存布局一致：同一模板克隆，或至少对所有 agent 用同一个随机化布局（像 Android zygote：对外仍然随机，对内一致）。按关掉随机化的近似，Chromium 的可省量能从 20% 升到 57%，每个 agent 约省 86 MiB。代价是同一宿主上的 agent 共享布局，一个 agent 泄露地址就等于泄露所有 agent 的地址；需要和隔离目标一起权衡。
- 页级合并仍然受指针差异限制：一页里只要有一个字节不同就不能合并。更细的共享要靠压缩，或相对模板做差分后压缩，见下一步。

不能据此下定论的地方：

- `setarch -R` 只关掉内核层面的随机化。Chromium 的 PartitionAlloc 和 V8 还有自己的随机化，所以对 Chromium 来说这仍是克隆收益的下限；真正的模板克隆还会保留未写过的页，收益更大。
- 应用基本空闲，只做了两步；运行时间更长、数据更多后，堆里各 agent 自己的数据占比会上升，重复比例会下降。
- 每组 1 次，arm64。没有测 KSM 本身的扫描 CPU 开销。

## 比页更细：压缩与模板差分（2026-11-18，已测）

按页合并受指针差异限制：一页里只要有一个字节不同就不能合并。这一节用同一批页内容测比页更细的几种存法。

### 方法

在上面的第二次扫描时保留每个非零匿名页的内容（按物理页去重），应用退出后离线计算以下几种存法的大小。零页一律按 0 计，只算 8 个 agent，不含合成器。压缩用镜像里已有的 libzstd、liblz4（`bench/compress.py`）。

| 存法 | 含义 | 对应的机制 |
|---|---|---|
| 原始 | 常驻匿名页 | 现状 |
| 按页合并 | 相同内容的页只存一份 | KSM |
| 按页压缩 | 每页单独 lz4 压缩，压不到 3/4 页的按原样存 | zram、zswap |
| 合并后按页压缩 | 先按页合并，再对每个不同内容单独压缩 | KSM 加 zram |
| 整体压缩 | 每个 agent 的全部非零页连成一个流，zstd 3 级、256 MiB 窗口、长距离匹配 | 空闲 agent 整体压缩存放 |
| 模板差分 | a0 作模板按整体压缩存；其他 agent 与模板内容相同的页免费，其余页以模板为参考数据压缩 | 相对模板的增量快照（`zstd --patch-from`） |

这一组和上一节是两次独立运行。两次的按页合并结果相差不到 5 MiB（例如 Chromium 249 对 244），可以当作一次重复。

### 结果

第一个之外每个 agent 的平均大小（MiB），也就是有了模板之后每多一个 agent 的成本：

| 应用 | 地址随机化 | 原始 | 按页合并 | 按页压缩 | 合并后按页压缩 | 整体压缩 | 模板差分 |
|---|---|---|---|---|---|---|---|
| Text Editor | 开 | 121 | 85 | 24 | 24 | 11.6 | 10.8 |
| Text Editor | 关 | 121 | 74 | 24 | 21 | 11.6 | 9.0 |
| Writer | 开 | 140 | 107 | 29 | 28 | 11.9 | 10.7 |
| Writer | 关 | 140 | 86 | 29 | 21 | 11.9 | 7.6 |
| Chromium | 开 | 150 | 120 | 42 | 37 | 17.5 | 15.6 |
| Chromium | 关 | 150 | 61 | 42 | 16 | 10.9 | 6.3 |

8 个 agent 合计（MiB，地址随机化开）：Text Editor 967 → 按页合并 678 → 按页压缩 194 → 整体压缩 93 → 模板差分 87；Writer 1122 → 876 → 229 → 95 → 87；Chromium 1196 → 965 → 337 → 140 → 127。计算这几种存法共花 5–8 s。

### 解读

- **压缩比共享大一个数量级。** 按页合并每个 agent 只省 20–30%，按页压缩省 70–80%（3.5–5 倍），整体压缩省 88–92%（8–12 倍）。这些应用的匿名内存非常稀疏：大量页只写了一小部分，其余是零或重复的结构。所以就省内存而言，主要杠杆是压缩，而不是让 agent 之间共享。
- **整体压缩比按页压缩再好 2–2.5 倍。** zram 每页独立压缩，看不到页与页之间的重复；把一个 agent 的内存当作一个流压缩，能利用跨页的重复。这就是"按页太粗"在压缩层面的体现。
- **跨 agent 的字节级冗余是存在的，但比想象的小。** 有地址随机化时，模板差分只比各自整体压缩再少 7–11%；关掉随机化后少 22–42%（Chromium 10.9 → 6.3 MiB）。也就是说，一旦按 agent 整体压缩，绝大部分冗余已经在 agent 内部被吃掉了，跨 agent 共享只是锦上添花。
- **地址随机化对压缩的影响比对按页合并小得多。** 按页压缩和整体压缩在开关随机化时几乎一样，只有用到跨 agent 内容的两种存法（按页合并、模板差分）才受它影响。

### 对设计的含义

agent 每步大约 24 s 里大部分时间在等模型，而 Heddle 通过控制接口准确知道一个 agent 什么时候空闲、什么时候会有下一个动作。这给了通用操作系统没有的条件：可以在一步结束后把空闲 agent 的匿名内存整体压缩存放，在下一个动作到来前（甚至在模型开始返回时）解压回来。

按这组数据粗算：共享 `/usr` 后每个 agent 的边际成本约 156–196 MiB（[内存曲线](memory.md)），其中匿名页 120–150 MiB。若空闲时匿名页整体压缩到 11–18 MiB，窗口缓冲另行释放或压缩，一个空闲 agent 只占几十 MiB。如果大部分 agent 在任一时刻都处于空闲，同样的内存能多放约 3–4 倍的 agent。这是推算，还没实现和测量。

需要测量才能确认的：

- **解压延迟。** zstd 解压通常每核 1 GiB/s 以上，150 MiB 约 0.1–0.2 s，相对模型调用的几秒可以接受，但要在实际机制里测。
- **可实现的粒度。** "整体压缩"需要一次换出、换入整个 agent。现有内核机制里，zram、zswap 按页压缩，对应的是"按页压缩"一列（3.5–5 倍）；近期内核支持对大页（多页 folio）一起压缩，介于两者之间。要拿到整体压缩的倍数，可能需要在用户态整体冻结并转存进程内存（类似 CRIU 或虚拟机快照），或者用 cgroup 的 `memory.reclaim` 加按大块压缩的交换后端。
- **真实负载。** 这里应用基本空闲，刚启动的堆非常稀疏，压缩比偏高。打开网页、文档、运行扩展后，内存里会有更多图片、文本等真实数据，压缩比会下降。

下一步：先用现成的内核机制做一版"空闲时回收"：一步结束后对 agent 的 cgroup 写 `memory.reclaim`，把匿名页压到 zram 或 zswap，下一步动作到来时测缺页数和截图延迟。这能给出"按页压缩"一列在真实机制下的收益和代价；整体压缩作为后续优化。

## 匿名内存里是什么（2026-11-19，已测）

前两节只看了能省多少，这一节看匿名内存由什么组成。`ksmscan.py --anatomy` 在第二次扫描时按三个维度拆分每个 agent 的匿名页（`bench/anatomy.py`）：

- 进程角色：Chromium 按 `--type` 区分浏览器、渲染、zygote、GPU、网络服务等进程。
- 所在内存区：malloc 堆、按大小分的匿名映射、库被重定位改写的私有页。
- 页内容特征，按顺序取第一个符合的：全零；稀疏（至少 75% 字节为零）；文本（大部分是可打印 ASCII）；指针密集（至少 1/4 的 8 字节字指向本进程已映射的地址）；不可压缩（lz4 压不到 3/4）；其他。每 4 页抽 1 页判定。V8 开了指针压缩，堆里是 32 位偏移，会落进"其他"。

每个应用 4 个 agent，地址随机化开，下表是每个 agent 的平均值（MiB）。

### 构成

| | Text Editor | Writer | Chromium |
|---|---|---|---|
| 匿名页合计 | 121 | 140 | 150 |
| malloc 堆 | 91 | 110 | 0.4 |
| 1–16 MiB 匿名映射 | 13.5 | 16.2 | 75（PartitionAlloc、V8） |
| 小于 1 MiB 匿名映射 | 5.4 | 2.9 | 16 |
| 库重定位后的数据 | 8.5（其中 LLVM 5.4） | 6.5（其中 LibreOffice 主库 4.8） | 51（其中 Chromium 主程序 49.5） |
| 指针密集 | 55 | 60 | 73 |
| 稀疏 | 27 | 33 | 38 |
| 全零 | 25 | 0.7 | 14 |
| 其他 | 13 | 47 | 20 |
| 文本 | 0.2 | 0.4 | 4.2 |
| 不可压缩 | 0.2 | 0.2 | 1.3 |

各类的 lz4 压缩比：指针密集约 3 倍，稀疏 7–9 倍，"其他"在 Text Editor 和 Writer 是 8–10 倍、在 Chromium 是 2.6 倍（V8 压缩指针和数值）。

Chromium 按进程：渲染进程 55（稀疏 19、其他 14、指针 10、全零 7、文本 3.7），浏览器进程 41（指针 25），zygote 30（指针 25），网络服务 17（指针 13），GPU 进程 3，存储服务 2。zygote 和网络服务的指针页主要是 Chromium 主程序重定位后的只读数据（RELRO）：49.5 MiB 每个 agent，约占 Chromium 匿名内存的三分之一。

### 逐项关掉：Text Editor

GTK4 在没有 GPU 时用 Mesa 的 llvmpipe 做软件 OpenGL 渲染，会加载 LLVM 并即时编译着色器。分别关掉 GL 渲染（`GSK_RENDERER=cairo`）和无障碍（`GTK_A11Y=none`），每种 2 个 agent：

| 配置 | 每个 agent 匿名页 | malloc 堆 | 1–16 MiB 映射 | 全零 | 指针密集 |
|---|---|---|---|---|---|
| 默认（GL，llvmpipe） | 128 | 92 | 13.5 | 27 | 55 |
| cairo 渲染 | 28 | 15 | 0.3 | 0.6 | 11 |
| 关无障碍 | 123 | 89 | 13.3 | 26 | 53 |
| cairo 加关无障碍 | 24 | 13 | 0.2 | 0.5 | 8.5 |

两种渲染器的截图逐像素看起来一样。cairo 下连续 5 次截图的延迟是 414–462 ms，默认是 310–346 ms，每次多约 100 ms，因为 cairo 每帧整窗重画、合成帧更多。

### 解读

- **Text Editor 的匿名内存约 80% 是 GL 软件渲染的开销。** 换成 cairo 后每个 agent 从 128 MiB 降到 28 MiB（4.6 倍），全零页和 1–16 MiB 映射几乎消失，堆从 92 降到 15 MiB。这部分是 llvmpipe 的状态：LLVM 编译器的数据结构、JIT 出的着色器、纹理和帧缓冲。对 agent 来说它只是"把界面画成像素"的手段，换一个更朴素的渲染器就能去掉。
- **无障碍只占约 4%（4–5 MiB）。** 它是 agent 获取控件树的途径，保留。
- **Writer 的大头是 LibreOffice 自己的堆（110 MiB）。** 没有 GL 这一块；"其他"类 47 MiB 压缩比约 10 倍，多半是大型数组和表格结构，具体是什么需要按调用栈统计 malloc 才能确定。
- **Chromium 分散在多个进程里，最大的一块是自己的重定位数据。** 49.5 MiB 的 RELRO 每个 agent 一份（同一 agent 内 zygote 派生的进程已经写时复制共享），这是上面关掉地址随机化后能跨 agent 合并的那部分；渲染进程里真正和页面有关的内容（DOM、样式、JS 堆、文本）只占一部分。
- **应用"状态"本身很小。** 文本类内容每个 agent 0.2–4 MiB；指针密集的对象图 55–73 MiB 主要是工具包、渲染器和库的结构，不是任务数据。

### 对设计的含义

- `heddle-run` 可以对 GTK4 应用默认设 `GSK_RENDERER=cairo`：Heddle 本来就只有软件渲染，GL 路径在这里只带来内存开销。代价是截图慢约 100 ms，在模型调用的秒级延迟面前可以接受。这和"去掉对 agent 无用的机制"是同一类优化，而且只改一个环境变量。
- 对 Chromium，类似的开关是 `--disable-gpu` 之外的软件合成选项、关掉 GPU 进程、限制渲染进程数，以及共享 RELRO（Android 上的做法）。这些还没测。

不能据此下定论的地方：每组 1 次，应用基本空闲；内容分类是启发式的；"其他"类的具体来源没有查清；cairo 渲染的 CPU 开销没有测。
